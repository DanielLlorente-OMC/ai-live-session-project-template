Píldora de conocimientoGitHub desde cero: tu proyecto y sus versiones

GitHub es un servicio para guardar y compartir proyectos. Puede alojar código, diseños documentados, textos y otros archivos. En el taller lo usaremos para conservar el trabajo y su historial.

Un repositorio es el espacio de un proyecto: reúne sus archivos, carpetas e historial de cambios. Piensa en una carpeta que permite consultar cómo ha evolucionado el trabajo.

El control de versiones permite guardar hitos y comparar cambios. Puedes ver qué se modificó, quién lo hizo y recuperar contenido de una versión anterior. Los cambios sin guardar en el historial no quedan protegidos por arte de magia.

Git y GitHub son cosas distintas. Git es la herramienta que gestiona el historial; GitHub aloja repositorios en internet y facilita compartirlos y colaborar.

Una rama es una línea de trabajo dentro del repositorio. Por ejemplo, puedes probar otra paleta en una rama sin cambiar la versión principal. Si te convence, integras sus cambios; si no, puedes conservar la principal.

Hoy empezaremos con la rama principal. No necesitas aprender todos los comandos ni crear ramas para completar esta primera práctica.

Un ejemplo sencillo

Tu repositorio puede contener la home, sus estilos, las referencias y decisiones. Cada commit sirve de hito: primera home, cambio de paleta y ajuste responsive. Una rama permite probar una alternativa sin modificar directamente la principal. En esta primera práctica basta main.

Interface Design: skill y distribución cómo plugin

Su núcleo es una skill para diseño de producto, con referencias y memoria de decisiones. Tambien se distribuye cómo plugin con comandos de revisión. Eso no significa que se ejecuten varios agentes autónomos.

Conector / MCP

Píldora de conocimientoCommit, ramas y colaboración: qué significa cada cosa

Commit: un punto guardado en el historial, con un mensaje que explica el cambio. Ejemplo: «Primera home revisada».

Push: enviar tus commits al repositorio de GitHub. Pull: traer e integrar los cambios del remoto en tu copia. Guardar un archivo no equivale a hacer commit y un commit local no equivale a subirlo.

Rama (branch): una línea para trabajar en una mejora. main: el nombre habitual de la rama principal. Merge: integrar los cambios de una rama en otra.

Pull request: una propuesta para revisar e integrar cambios en GitHub. No es lo mismo que pull. En proyectos compartidos ayuda a revisar antes de incorporar trabajo.

Ejemplo: conservas la home inicial en main, pruebas otro diseño en una rama y comparas. Si lo apruebas, lo integras. Git conserva el historial de los commits; los conflictos entre cambios pueden requerir revisión.

Repositorio privado: limita quién puede acceder. Revisa siempre los archivos antes de subirlos y comprueba que el remoto apunta a tu repositorio, no a la plantilla común.

Antes de subir

Comprueba destino y visibilidad privada. Revisa la lista de archivos, excluye claves y archivos personales y escribe un mensaje de commit concreto. Si trabajas desde una copia clonada del curso, el remoto inicial puede seguir apuntando al repositorio común: hay que cambiarlo antes del push.

Para ampliarPracticar commits y pull requests

Tres momentos: commit, push y pull request

En el taller hemos simplificado el recorrido para aprender el entorno. En un proyecto compartido podemos distinguir tres momentos. Son acciones habituales de Git y GitHub, no niveles de confidencialidad ni tres copias de la documentación.

  1. Commit · guardar una versión local. Agrupa un cambio coherente y explica qué has hecho. Incluye la documentación afectada por ese cambio, si corresponde. Todavía no se ha enviado a GitHub.
  2. Push · subir esa versión. Envía los commits a la rama del repositorio remoto. El equipo ya puede consultarlos si tiene acceso. Subir no significa que el cambio esté aprobado, integrado en main o publicado en el producto.
  3. Pull request · proponer la integración. Abre una solicitud para revisar los cambios de una rama frente a otra. Explica el motivo, qué cambia, cómo se ha comprobado y qué documentación se actualiza. La revisión puede pedir ajustes antes de aprobar.

Después viene el merge: integra la propuesta en la rama de destino cuando se cumplan las revisiones y comprobaciones acordadas. El despliegue o la publicación del producto es otro paso, según el proyecto.

Ejemplo: en la rama mejora-formulario modificas el formulario y su documentación; haces commit, push y abres una pull request hacia main. Otra persona revisa el resultado, se corrige lo necesario y se integra.

Pull no es pull request: pull trae e integra cambios del remoto en tu copia de trabajo; una pull request propone integrar cambios entre ramas en GitHub.

Local y GitHub son la copia de trabajo y su remoto versionado. La documentación vive en una ubicación acordada dentro del proyecto y evoluciona con los cambios; no hace falta escribir un documento diferente para cada momento.

Ampliación para trabajo en equipo. La práctica inicial sigue siendo válida con commit y push a tu repositorio privado; no exige crear una pull request en este primer ejercicio.
